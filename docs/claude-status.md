# Claude ステータス

Claude Code エージェントの状態を検知して表示する。

## 状態定義

エントリが無い状態（`undefined`）は Claude 未起動を表す。

| 状態        | 意味                                 | 通知 | UI                              |
| ----------- | ------------------------------------ | ---- | ------------------------------- |
| `undefined` | 未起動（端末はあるがセッションなし） | 不要 | インジケーターなし              |
| `idle`      | セッション開始済み、プロンプト待ち   | 不要 | 緑の塗り丸                      |
| `working`   | 作業中                               | 不要 | リング + spin + 経過時間        |
| `asking`    | 承認待ち                             | 必要 | 橙の塗り丸 + pulse              |
| `done`      | 応答完了、人間の確認待ち             | 必要 | 緑チェック + メッセージ吹き出し |

## 状態遷移

```text
undefined ──セッション開始──→ idle ──タイトル: 稼働中──→ working ──承認要求──→ asking
                               ↑                          ↑    ↖                   │
                               │                          │     └─タイトル: 稼働中─┘
                               ├──タイトル: 待機中────────┘   （承認後の再開）      │
                               │  （中断 / プロンプト復帰）                          │
                               ├──画面: 承認 UI の消失────────────────────────────┘
                               │                          ↓ ターン終了
                             idle ←──既読消化──────────── done
                               │
                    端末終了 / セッション終了
                               ↓
                            undefined
```

## 検知信号の使い分け

**同じ状態を複数の信号から動かさない**。信号ごとに担当する遷移を固定する。

| 信号               | 担当する遷移                                           |
| ------------------ | ------------------------------------------------------ |
| ウィンドウタイトル | `working` への進入、`working` からの `idle` 離脱       |
| hook               | `idle`（開始）/ `asking`（進入）/ `done`（ターン終了） |
| 画面本文           | `asking` からの離脱のみ                                |

### なぜ working / idle をタイトルで取るか

> [!WARNING]
> Claude Code にはユーザー中断（Ctrl+C / Escape）を通知する hook が存在しない。テキスト生成中の
> 中断ではターン終了の hook も失敗の hook も発火しない。

このため working / idle を hook では取らず、**Claude がタイトル先頭に常時出す状態プレフィックス**
から導く。中断も通常完了も「稼働中 → 待機中」の 1 経路で拾えるので、**中断専用の検知（出力の
文字列マッチや入力キーの推論）が不要になる**。

- 稼働中と待機中はそれぞれ専用の文字で表される。**分類と表示用の除去は同じ文字集合を SSOT として
  共有する**（サイドバーに出す Task タイトルからはこのプレフィックスを落とす）
- **稼働中のプレフィックスは常に `working` にする**（新しいターンの開始・中断後の再開の確証）
- **待機中のプレフィックスは `working` からの離脱時にだけ `idle` に倒す**。`done` / `asking` は
  温存する（hook 権威。**未読の `done` をタイトルで消さない**）
- `done` から次に稼働中が観測されたら `idle` を経由せず直接 `working` へ遷移する
- **全 worktree の端末は非表示でもマウントされ続ける**ため、非アクティブな worktree でも状態が
  即時更新される（ポーリング不要）

### なぜ asking の離脱を画面本文で取るか

`asking` に **入る**のは hook 権威だが、**承認せずキャンセル / 中断で抜ける hook は存在しない**。
タイトルも使えない — 承認プロンプトの表示中もキャンセル後も同じ待機中プレフィックスになり、
**タイトルだけでは 2 状態を区別できない**。よってタイトルの待機中では `asking` を落とさない
（落とすと承認プロンプト表示中にバッジが消える）。

離脱の信号には **可視画面に承認 UI の文言があるか**を使う。`asking` のときだけ画面本文を読み、
文言が消えた時点で `idle` に戻す。発火点は描画確定のタイミングで、タイトル変化ではなく画面変化を
拾う。

承認して再開したケースは同じ書き込みの中でタイトルの稼働中が先に処理されて `working` に倒れるため、
**画面本文が担うのは離脱だけ**。

## hook イベントの対応

| hook                 | gozd イベント    | 状態への作用                                 |
| -------------------- | ---------------- | -------------------------------------------- |
| `SessionStart`       | `session-start`  | `idle`                                       |
| `SessionEnd`         | `session-end`    | `undefined`（エントリ削除）                  |
| `Stop`               | `done`           | `done`（保留作業があれば表示のみ `working`） |
| `PermissionRequest`  | `needs-input`    | `asking`（即時ではない。下記の条件）         |
| `StopFailure`        | `stop-failure`   | `done`                                       |
| `UserPromptSubmit`   | `running`        | なし（効果の発行と、承認要求の取り消しのみ） |
| `PostToolUse`        | `tool-done`      | なし（同上）                                 |
| `PostToolUseFailure` | `tool-failure`   | なし（承認要求の取り消しのみ）               |
| `SubagentStart`      | `subagent-start` | なし（teammate 台帳への追加のみ）            |
| `SubagentStop`       | `subagent-stop`  | なし（台帳から除去 → done 表示の回復）       |
| `TeammateIdle`       | `teammate-idle`  | なし（同上 + 通知の in-flight マーカー）     |

送信経路の選択基準は [architecture.md](architecture.md#送信経路の使い分け)。

### 承認要求が UI に出る条件

承認要求を受けても即座に `asking` へ遷移しない。**続けて「その呼び出しが自力で抜けた」ことを示す
イベント（実行中 / 完了 / ツール完了 / ツール失敗 / セッション終了 / 停止失敗）が届かなかったときにだけ**
`asking` に入る。

これにより **自動承認で一瞬で抜けるツール呼び出しではバッジが瞬かず、人間が本当に止まる承認だけが
UI に出る**。待っている間にセッションが消えていた場合は遷移しない。

## 既読の消化

既読消化は `done` → `idle` の遷移（セッションは生きている）。

**発火点は worktree 選択の 1 か所**。サイドバーのクリック、端末のフォーカスなど、すべての worktree
選択経路が同じ更新を通る。

## 真の done と「保留作業がある偽 done」

ターン終了の hook は「セッション終了」ではなく **「主エージェントのターン終了」**で発火する。
エージェントが background 実行や予約された再起動を仕掛けるとその時点でターンが終わって hook が
飛ぶが、裏の作業が終わると Claude は自動で再起動する。**このとき完了バッジと音声通知を出すと、
人間は「終わった」と誤認する**。

同期実行のサブエージェントは完了まで主エージェントのターン終了を出さない。よって
**偽 done の発生源は非同期の作業だけ**に限定される。

区別の信号はターン終了 hook が渡す 2 つの配列（走行中の background エンティティ、予約された再起動）で、
これを 1 つの「保留作業あり」信号に畳む。ただし **teammate 型のエントリは数えない**（後述）。

### 保留があっても状態は必ず done に倒す

**保留作業があっても状態は常に `done` にする**。保留はフラグとして保持し、**バッジの描画時に
`done + 保留` を `working` として見せる**。保留が空になった本物のターン終了でフラグが落ち、表示が
`working` → `done` に切り替わる。

`working` を直接維持しない理由は **状態固着の回避**。ターン終了後に Claude が再起動しないケース
（完了通知の欠落 / 予約再起動の不発）では「次のターン終了」が永久に来ない。`working` を維持すると
その状態に張り付き、**`done` でしか効かない既読消化の経路も失う**。`done` を経由させることで、
再起動が来なくてもフォーカスで `idle` に消化でき、完了通知が永久に出ない事故を防ぐ。

### teammate の稼働判定

teammate（名前付きで spawn される常駐エンティティ）は使い捨てのサブエージェントと寿命モデルが違う。
使い捨ては完了すると配列から消えるが、**teammate は idle 化してもセッション終了まで残り続ける**。
配列の長さで判定すると、一度 teammate を spawn したセッションが永続的に working 表示になる。

このため teammate は長さ判定から除外し、稼働中かどうかは **サブエージェントのライフサイクル hook で
維持する台帳**で判定する。

- **開始**: teammate 形状の識別子だけを台帳に追加する。再開でも発火し、resume された teammate は
  行を再獲得する
- **停止**: 台帳から除去する。**除去で台帳が空になったら、次のターン終了を待たず表示を done に
  回復する**（lead を再起動しない終了経路があるため）。この回復では効果を発行しない（完了通知は
  ターン終了側が担う）
- **idle 通知**: 台帳から除去し、同時に **配送中マーカー**を立てる（後述）
- **ターン終了時に teammate が 1 件も無ければ台帳とマーカーを掃除する**。ターン終了が渡す配列は
  完全な台帳なので、lifecycle hook を取りこぼした残留をここで回復できる

### 真の done の条件は「システム全体の静止」

```text
done = lead がターンを終えている
     ∧ 全 teammate が idle（台帳が空）
     ∧ 配送待ちメッセージが無い
     ∧ 予約された再起動が無い
```

3 行目が必要なのは、**teammate が idle 化するとき必ず idle 通知を lead へ発射する**ため。lead が
稼働中だと通知は滞留し、**lead のターン終了直後に配送されて lead を再起動する**。このとき
「teammate idle + lead 停止」という静的状態が配送の前後で 2 回現れ、配送前を done にすると
完了通知が二重に鳴る。分散システムの終了検知（全プロセスが idle でも転送中メッセージがあれば
未終了）と同じ構造。

hook はチャネル内のメッセージを見せないため、**発射と消化の観測で橋渡しする**。

- **発射の観測**: idle 通知の受信でマーカーを立てる
- **消化の観測**: lead の新しいターンの開始でマーカーを消す。ターン開始はユーザープロンプト、
  または **done / idle → working の遷移**で観測する。**asking → working（承認後の同一ターン再開）は
  ターン境界を跨いでいないため消化しない**

既知の残存リスク（hook にメッセージの可視性が無い以上、マーカーは近似）:

- **通知の欠落**: 再起動が来ないと working 表示が残る。保留作業と同型の故障モードで、状態機械が
  `done` を経由しているため既読消化で救済される
- **複数 teammate の同時 idle**: マーカーは端末単位の真偽値のため、複数の通知が別ターンに分かれて
  配送されると完了通知が再度鳴りうる。**失敗様態は「通知が余分に鳴る」で、状態固着はしない**
- **hook 到達順の逆転**: 開始通知がターン終了より遅れると終局判定が 1 ターン早まりうる。
  ソケットの逐次キューが送信順を保証しており通常は起きない

## 効果（音・演出・読み上げ）の抑止は 1 か所に集約する

「保留付きの done を完了扱いするか」の判断を購読者ごとに散らすと、購読者を増やすたび取りこぼす。
これを防ぐため、**効果は hook を解釈した結果として再発行する正規化イベント 1 本に集約する**。

- 保留付きの done や既に死んだ端末など「完了扱いしない」ケースは、**この 1 か所で落とす**
- 効果側（読み上げ・演出・効果音）は正規化イベントを購読するだけで、保留の有無を一切見ない。
  **落とされたイベントは構造的に届かないため、新しい購読者を足しても取りこぼせない**

保留フラグを読む判断点はバッジ側と効果側の 2 経路あるが、いずれも同じフラグを参照する。バッジは
表示状態、効果はイベント駆動で出力先が異なるため責務として分離している。

> [!NOTE]
> ターン終了 hook が保留の配列を渡さない場合は「0 件（保留なし）」として扱う。欠落と空は同義。

## サイドバーの表示ルール

1 つの worktree に複数の端末がある場合、優先度順にソートして表示する。

| 状態      | 優先度    |
| --------- | --------- |
| `asking`  | 3（最高） |
| `working` | 2         |
| `done`    | 1         |
| `idle`    | 0（最低） |

吹き出しの内容:

- `done`: 最後のアシスタントメッセージの一行目
- `asking`: 質問形式の承認要求なら質問テキスト
